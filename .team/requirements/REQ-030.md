## Requirement

Regression tests of the admin screens (real sign-in, page access per role, a save per form) run with every change (D-030; Q-076)

## Acceptance criteria

Recorded by the architect on 2026-11-11 (T-065) from Q-076 and D-030; the user still confirms them.
- Given the test project, when `dotnet test` runs without Docker and without a running stack, then the admin frontend is hosted in memory against the in-memory API and the screen tests run in that normal run, with no extra category or switch (D-039).
- Given a fictitious user per role, when the test signs in through the real sign-in page (and the two-factor step for a user who has it on), then it gets the auth cookie; with a wrong password it stays on the sign-in page.
- Given every admin page, when it is opened anonymously, then it redirects to sign-in; by a role that the authorization matrix allows, then 200 with its key content (list rows, form fields, totals); by any other role, then the access-denied page.
- Given every form (owners, assets, VAT rates, expenses, activities, invoices with mark paid, users, roles, profile), when a valid save is posted, then the saved data shows on the next page; when an invalid one is posted, then the field errors show.
- Given any change to the code, then these tests pass before its pull request is ready; every test carries its `Requirement` and `TestCase` traits (D-027).
- Who runs them (Q-081; there is no pipeline): the developer or tester of the change runs the full `dotnet test` before every commit and records the result (passed, failed, skipped) in the task report; the orchestrator checks that record before a pull request is made ready. A pipeline would be new scope.
