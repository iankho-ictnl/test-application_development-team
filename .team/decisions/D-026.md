## Decision

Restructure the code to the layout of skill 2026-11-09.4, literally. Supersedes D-021 (its
`Features/V1/...` level and its shared contracts DTOs no longer fit the rules).

Projects:
- `PropertyAdmin.Api`: endpoints and contracts only. `V1/<Feature>/<Feature>Controller.cs` (one
  thin controller per feature) and `V1/<Feature>/<UseCase>/Request.cs`, `RequestValidation.cs`,
  `Response.cs`, `Mapping.cs`, `Models/`. Cross-cutting code (central error handler of D-022,
  authentication set-up, `Program.cs`) stays outside `V1/`.
- `PropertyAdmin.Logic` (new class library): `V1/<Feature>/I<Feature>Service.cs`,
  `<Feature>Service.cs` and `V1/<Feature>/<UseCase>/Query.cs` or `Command.cs`, the handler, its
  validation, `Result.cs`, `<Source>Mapping.cs`, `Models/`. Commands run in a transaction;
  queries are `AsNoTracking` with projection. The feature service is the only part that uses the
  data access. No MediatR (commercial licence, REQ-016): handlers are plain classes registered
  in DI.
- `PropertyAdmin.Data` (new class library): `AppDbContext`, entities, migrations, seeder.
  Entities never leave this project and `PropertyAdmin.Logic`.
- `PropertyAdmin.Contracts`: removed. The frontend gets its own models.
- Frontend: an API client layer `Services/Api/V1/<Feature>/<Feature>Client.cs` with its own
  `Models/` (response models of the frontend) and `Mapping.cs` (API response to view model);
  pages use only these. Its own permission-name constants replace `Contracts/Permissions.cs`.
- Routes `/api/v1/<feature>`. Tests mirror `V1/<Feature>/<UseCase>/`.

Features: Auth, Users, Owners, Assets, VatRates, Expenses, Activities, Invoices, Reports; one
use-case folder per existing action, named after what it does (for example `GetAll`,
`GetDetailsById`, `Create`, `Update`, `MarkPaid`, `GetPdf`, `GetAssetResults`,
`GetOwnerOverview`, `Login`, `LoginTwoFactor`).

## Why

Deviations found in the code (T-028, 2026-11-09):
1. `Controllers/` folder instead of `V1/<Feature>/`; no version level.
2. Several controllers per file: `MasterDataControllers.cs` (3), `TransactionControllers.cs` (4).
3. Controllers use `AppDbContext` directly and hold logic and mapping.
4. No separate logic project: services live in `PropertyAdmin.Api/Services/`.
5. No commands and queries with handlers and validation per use case.
6. One shared mapper (`Services/Mapper.cs`) instead of mapping per use case and per boundary.
7. Data access inside the API project (`Data/`), so the API can reach entities.
8. All request and response models in one file (`PropertyAdmin.Contracts/Dtos.cs`).
9. A contracts project shared with the frontend, without a decision.
10. The frontend uses the API's DTOs directly; no own models or mapping in `ApiClient.cs`.
11. Routes have no version (`api/owners`).
12. Tests do not mirror a use-case structure.
13. D-021 itself puts a `Features/` level in front of `V1/` and keeps the shared DTOs.

Rejected: keep one project (small solution) - rejected because the rules ask for a separate
logic project and the API already has 4 services; keep the shared contracts project - fewer
files, but couples the frontend to the API's models; MediatR - licence (REQ-016).

Impact: no database change, no behaviour change; API routes change to `/api/v1`. 28 story
points, replacing the 8 of D-021:
- B7 backend-developer-1 (3): create `PropertyAdmin.Logic` and `PropertyAdmin.Data`, move
  `Data/`, DI registration; build green.
- B8 backend-developer-1 (5): Owners, Assets, VatRates as V1 slices.
- B9 backend-developer-1 (3): Expenses, Activities as V1 slices.
- B10 backend-developer-1 (5): Invoices (incl. PDF) and Reports as V1 slices.
- B11 backend-developer-1 (3): Auth and Users as V1 slices; remove `Controllers/`, `Services/`
  and the reference to `PropertyAdmin.Contracts`.
- F4 frontend-developer-1 (5): own API client layer per feature with own models and mapping,
  `/api/v1` routes, own permission constants; remove the reference to `PropertyAdmin.Contracts`.
- T3 tester (3): move and extend the tests to mirror `V1/<Feature>/<UseCase>/`; remove the
  `PropertyAdmin.Contracts` project once B11 and F4 are done.

Order: T-029 (D-022) first, because it touches every controller; then B7; B8 to B11 one after
the other (one backend developer); F4 after B8 to B11 (routes); T3 last. Risk: together with
the open work this exceeds the 40-hour project boundary; the user may choose to phase it.

Accepted by the user, 2026-11-09.
