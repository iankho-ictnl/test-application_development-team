## Decision

`SignInRateLimiter` (singleton, built-in `System.Threading.RateLimiting` fixed window, no queue) allows 10 POSTs per 60 seconds per client IP address, counted apart for the password step (Login) and the two-factor step (LoginTwoFactor). Configurable with `SignInRateLimit:PermitLimit` and `SignInRateLimit:WindowSeconds`. The page handler asks it first, before validation and before the API call; a refusal returns the same page with status 429 and the localized message "Too many sign-in attempts. Wait a minute and try again." The client IP comes from the forwarded headers of the known proxy (D-023). The API's own account lock-out stays as it is.

## Why

The ASP.NET Core rate-limiting middleware (`[EnableRateLimiting]`) refuses with an empty 429 response that is not localized and not a page; checking in the handler gives the user a readable page. Per IP and per step: one client cannot exhaust the attempts of another, and a correct password does not consume the two-factor attempts. A distributed store is not needed: the frontend runs as one container (REQ-017). Rejected: a limit per user name (lets an attacker lock out a known user faster than the API lock-out does).
