## Decision

Interface contract changes from T-044 (old `/api/auth` and `/api/v1/auth` routes alike):
- `GET auth/2fa`: `sharedKey` and `authenticatorUri` are `null` while `enabled` is true (S-18).
- `POST auth/2fa/disable` takes `{ "password": string?, "code": string? }`: the current password or a current authenticator code (no recovery code). Neither given: 400; wrong: 400 and counted as a failed access (lockout after 5) (S-19).
- New `POST auth/logout` (fallback policy, own account only, user id from the token, no body): renews the caller's security stamp, 204; every token of the user gets 401 from then on (S-26).
- Role create and update refuse `ReadOwn` together with any other permission: 400 (S-28).
- Max lengths (400 when longer): user name 100, password 128, code 64, challenge token 4096 on login, login-2fa, 2fa/enable, 2fa/disable, password and the user-create password (S-24).
- An unknown or locked-out user name at login runs a dummy password-hash check, so it costs the same time as a wrong password (S-23).

## Why

The fixes the security officer prescribed in T-020; the field names and the 400s follow the existing own-account endpoints (`auth/password`). Rejected: a recovery code for disable (the finding names password or authenticator code only); a separate 401 for a wrong credential (the frontend would treat it as an expired sign-in). Logout is an own-account endpoint without a permission policy, so it must be listed in architecture.md and reviewed (Q raised).
