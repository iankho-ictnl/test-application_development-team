## Decision

Changed after the user's answer to Q-108 (2026-11-20, "add a language parameter in the api"). The API localizes, the frontend does not translate API text. Every API endpoint accepts the optional query parameter `lang` with `nl-NL` or `en-US` (case-insensitive); absent, empty or any other value gives Dutch (`nl-NL`), never an error. It sets only the UI culture (message texts); number and date formatting stay nl-NL (REQ-021). Built with ASP.NET Core's own `QueryStringRequestCultureProvider` (`QueryStringKey` and `UIQueryStringKey` = `lang`) as the **only** provider: `Accept-Language` is no longer read (no fallback). Field validation and business-rule messages come from the API's resource files (D-010), keyed by the English text; business rules through the central error handler as D-050 says. The frontend's ApiClient adds `lang=<CultureInfo.CurrentUICulture.Name>` to every call (a DelegatingHandler next to AccessTokenHandler) and shows the Problem Details `detail` (else `title`) as received. Replaces D-048 (its "detail before title" stays). S2: the owner messages only. Details and contract: architecture/error-handling.md.

## Why

The user asked for an explicit parameter: the language is visible in the call, testable by URL, and not changed by a browser, proxy or HttpClient default header. Accept-Language goes so there is one source and no hidden precedence. Rejected: a route segment `/api/{lang}/v1/...` (changes every route and the authorization endpoint list); a custom header (still hidden, not what was asked); keeping Accept-Language as fallback (two sources, the frontend never relies on it). Error codes translated by the frontend and D-048's exact-text lookup stay rejected as before.
