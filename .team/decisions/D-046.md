## Decision

Every "today" (inactive date D-045, the REQ-024 anonymization term, invoice and overdue dates) is the
local date of the system the app runs on (user, Q-102). API code takes it only from the injected
`TimeProvider` as `DateOnly.FromDateTime(time.GetLocalNow().DateTime)` (as `OwnerService` already
does); never `DateTime.UtcNow`/`DateTime.Today` or a fixed zone in code. Instants (tokens, lockout)
stay UTC. A Linux container does not see the host's zone, so `docker-compose.yml` passes
`TZ: ${TZ:?Set TZ (IANA time zone of this system, for example Europe/Amsterdam) in .env}` to `api`
and `web` (the frontend's date defaults use `DateTime.Today`), and `.env.example` lists `TZ`. The
`10.0-resolute` images already contain `tzdata` (runtime-deps Dockerfile, checked 2026-11-20): no
image change. Build pieces B16 and T12 in architecture/build-tasks.md (backend-developer-1 0.5 SP,
tester 0.5 SP, for REQ-002).

## Why

The user chose the system's local time (Q-102), not fixed UTC and not a zone in code. Rejected:
mounting `/etc/localtime` from the host (works on a Linux host only, not on Docker Desktop for
Windows, D-039); a default zone in compose (that would be an assumption, rule 4); a zone setting in
appsettings (that is a fixed zone in code, not the system's). Effect without TZ: containers run
in UTC, so near midnight "today" is one day early.
