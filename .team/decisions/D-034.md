## Decision

Replaces the last clause of D-005 ("role changes take effect at the next sign-in"); the rest of
D-005 stays. On every request, after the security-stamp and lockout check, the API replaces the
token's permission claims with the permissions of the user's current roles, read from the
database, so policies and `ReadScopeOwnerId()` use the current set. A permission removed from a
role is refused (403) at its members' next request; an added one is allowed at the next request.
Role permissions may be cached in memory only when every role create, update and delete clears
that cache after its transaction commits and before it returns (no time-based window). Fail closed: when the permissions cannot be
read, the request fails (500), never falls back to the token claims. The JWT keeps its claims
for the frontend menu only (stale until the next sign-in; the API enforces). Built in T-058.

Conditions of the security officer (Q-057, 2026-11-10; details in architecture.md, Authentication
and authorization): **C1** the user's roles are read from the database by user id and role id,
never from the token's role-name claims. **C2** the cache is cleared after the transaction
commits, never before, keyed by role id, in both the legacy `RolesController` and the V1 Roles
slice (D-035). **C3** every permission claim of the token is removed before the current ones are
added, and the owner-id claim is replaced from the loaded user. **C4** a failed read is never
caught to fall back to the token: 500 with a general Problem Details message (D-022). **C5** a user
whose roles give no permissions gets 403 on every endpoint with a permission policy; the own-account
endpoints (fallback policy) stay open to them, with the stamp, lockout, permission reload and C4
also running there (Q-058). **C6** deployment note:
restart the API after a role or permission change made straight in the database.

## Why

User chose option A in Q-055: REQ-012 as written ("next request"); S-10's 8-hour window ends for
role permissions. Rejected: a time-based cache (allows a removed permission for its lifetime,
against REQ-012); shorter tokens (still a window, more sign-ins); per-role security stamps that
force all members to sign in again (heavier for users). The in-memory cache assumes one API
instance (REQ-017, docker compose); scaling out needs a shared cache or no cache (a new
decision). Cost: one extra small query per request, cached. Reviewed by the security officer
(Q-057, design review D-034 in reviews/security-assessments.md): acceptable, no Critical or High
finding, with conditions C1 to C6.
