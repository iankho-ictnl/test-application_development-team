## Decision

One test per row of the error mapping in architecture.md: status, `application/problem+json`,
`status`, `title` and `traceId` present, and no exception text, stack trace, query or type name
in the body. 400 validation (with `errors`), 401, 403 and 404 through real requests. 500, 504
and 499 through a test double: the test host replaces one feature service in DI
(`ConfigureTestServices`) with one that throws (`InvalidOperationException` with a secret-looking
message; the exception agreed in Q-051; waits on the cancelled token). A test logger provider
checks the log level: 500 logged once as error, 499 at Debug with no error and no body. 409
after T-039, 422 after BUG-1. No test-only endpoint in production code (absolute rule 12).

## Why

The current tests check status and Problem Details only for 400 and some 404s; 401, 403 and
most 404s check the status only; 500, 499 and 504 are not tested through the API (only a
service-level cancellation test for Expenses); `traceId` and the absence of internal details are
never checked. Rejected: a test endpoint behind a configuration switch (would ship in
production). Impact: tester, 2 story points (replaces T2 of D-022).
